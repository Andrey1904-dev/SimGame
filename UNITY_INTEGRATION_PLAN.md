# LIFE FROM ZERO — план подключения модулей к Unity

Основано на аудите ТЗ №017 (`FULL_AUDIT_REPORT.md`).
Цель: подключить `LifeFromZero.Economy`, `LifeFromZero.Jobs.Delivery`,
`LifeFromZero.Phone`, `LifeFromZero.Debts` к Unity 6000.3.27f1 без изменения их
контрактов. Модули остаются обычными C#-библиотеками без Unity API — все мосты
живут на стороне проекта.

---

## 1. Порядок подключения

Каждый шаг заканчивается компиляцией и зелёным прогоном — не переходить дальше,
пока предыдущий шаг не собран.

| # | Шаг | Результат |
|---|---|---|
| 1 | Скопировать `Economy/`, `Jobs/`, `Phone/`, `Debts/` в `Assets/Modules/` целиком (asmdef уже внутри) | 4 runtime + 4 test asmdef видны в Unity |
| 2 | Скомпилировать runtime-сборки **без адаптеров** | 0 ошибок, 0 предупреждений «тип не найден» |
| 3 | Прогнать EditMode-тесты как есть | 259/259 (эталон — `MiniTestRunner`, но в Unity работают NUnit-обёртки) |
| 4 | Подключить `LifeFromZero.Economy` + `ShopService` к существующему `MoneyWallet`/`FoodInventory` | покупка хлеба работает, деньги и товары совпадают |
| 5 | Подключить `LifeFromZero.Debts` к тому же кошельку | платёж по долгу 38 400 ₽ списывает ровно один раз |
| 6 | Подключить `LifeFromZero.Jobs.Delivery` (время, локация, выплата) | полный цикл заказа с одной выплатой |
| 7 | Подключить `LifeFromZero.Phone` (реестр, сообщения, уведомления) + экраны | телефон не меняет деньги и заказы |

| 9 | Только после этого — сюжет, NPC, UI-полировка | — |

Почему такой порядок: Economy и Debts — фундамент денег; Delivery начисляет
деньги; Phone только читает. Если Phone подключить первым, ошибки отображения
будут маскировать денежные дефекты.

## 2. Необходимые адаптеры (пишет проект, не модули)

Ниже — минимальный список. Слева интерфейс модуля, справа — что должен сделать
адаптер поверх реальных систем игры.

| Интерфейс | Модуль | Обязанности |
|---|---|---|
| `IWalletAdapter` | Economy | `Balance` без побочных эффектов; `TrySpend` атомарно (всё или ничего, при `false` баланс не изменён); `TryRefund` возвращает ровно списанное. Исключения не пробрасывать (модуль гасит их, но диагностику потеряете). |
| `IInventoryAdapter` | Economy | `CanApprove` **без мутации** (проверка места); `TryAdd` без частичных добавлений. Если `FoodInventory` не умеет проверять вместимость — правило проверки реализуется здесь. |
| `IShopCatalog` | Economy | По умолчанию `ShopCatalog.CreateDefault()`; для нескольких магазинов — свой каталог. |
| `IGameClockAdapter` | Delivery | `NowMinutes`: монотонно не убывающие минуты с начала игры. NaN/∞ модуль считает отказом адаптера. |
| `ILocationProvider` | Delivery | `CurrentLocationId` — строка, совпадающая с `DeliveryPoint.Id` («bakery», «office_12»). |
| `IPayoutAdapter` | Delivery | `TryCredit(long)`. **Обязательно идемпотентно по заказу** (см. риск P1-7): повторное начисление той же суммы не должно увеличивать баланс дважды. |
| `IDebtClockAdapter` | Debts | `long NowMinutes`, целые минуты, не убывает. |
| `IDebtWalletAdapter` | Debts | `TryGetBalance`; **`TryDebit(paymentId)` идемпотентен** (повтор с тем же ID — `true` без второго списания); `TryRefund(paymentId)` идемпотентен; `TryWasDebited(paymentId)` читает **долговременный** журнал (переживает перезапуск), а не память. Вводите пространство имён для `paymentId` (например `"debt:" + id`), чтобы они не пересекались с операциями других систем. |
| `IPhoneClock` | Phone | `NowMinutes` (double), ошибки → `GameMinutes.Unknown` внутри модуля. |
| `IDeliveryJobsSource` | Phone | `TryGetOrders` / `TryGetActiveOrderId`. **Фазу отображать явно** `DeliveryOrderState → DeliveryJobPhase` (у Delivery есть `None = 6`, у Phone такого значения нет; прямое приведение `int` недопустимо). Отфильтровать заказы со `State == None`. |
| `IDebtsSource` | Phone | `TryGetDebts` → `DebtDto` c `DebtPhase` (заполнять из `DebtView.Status`). |
| `IBalanceSource` / `IStorySource` | Phone | `TryGetBalanceRubles(out long)`, `TryGetEntries`. Только чтение. |
| `IDebtEventSink` | Debts → Phone | `Publish(DebtEvent)` → `IPhoneNotifier.Push(...)` с **детерминированным ID** (см. §4). |

Правила для всех адаптеров:

* Не бросать исключений в штатных отказах — возвращать `false`. Модули гасят
  исключения, но теряют причину.
* Не вызывать методы сервисов изнутри адаптеров, если это не предусмотрено
  контрактом (реентрантность разобрана в Debts, но лучше её не создавать).
* Один экземпляр кошелька на игру; все адаптеры смотрят в него.

## 3. Совместимость с существующим Unity-проектом

* **Unity 6000.3.27f1, C# 9.** Модули проверены на отсутствие конструкций C# 10+.
  Не включайте в проекте `LangVersion` выше 9 без повторной проверки.
* **Сборки.** `noEngineReferences: true`, `references: []` — модули не видят
  `UnityEngine` и друг друга. Это и есть защита от циклических зависимостей.
* **Тестовые сборки.** Editor-only, `overrideReferences: true`,
  `precompiledReferences: ["nunit.framework.dll"]`,
  `defineConstraints: ["UNITY_INCLUDE_TESTS"]`, `autoReferenced: false`.
  Не переносите тестовые `.cs` в runtime-сборку.
* **Нет статического состояния.** Ни Singleton, ни `static`-полей с данными —
  экземпляры создаются загрузчиком/сценой. Это упрощает сохранение и тесты.
* **Поток.** Модули не потокобезопасны и рассчитаны на главный поток Unity
  (так и написано в `DebtEventHub`). Не вызывайте их из `Task`/фоновых потоков.
* **Деньги — только `long`.** Не конвертируйте в `float`/`double` на границе
  (Phone: `IBalanceSource` → `long`; Delivery: `long`; Debts: `long`;
  Economy: `Money.FromRubles(long)`).

## 4. Требования к сохранениям

### 4.1 Что сохраняется

| Что | Чем | Обязательно |
|---|---|---|
| Кошелёк (баланс + журнал операций/начислений) | система проекта | да |
| Часы игры (`NowMinutes`) | система проекта | да |
| Economy: журнал незавершённых возвратов | `ShopService.PendingRefunds` → `RestorePendingRefunds` | да |
| Debts | `DebtService.CreateSnapshot()` / `RestoreSnapshot(...)` | да |
| Delivery | `DeliveryService.CreateSnapshot()` / `RestoreSnapshot(snapshot, out error)` | да |
| Phone: сообщения | `CreateSnapshot()` / `PhoneMessagesRestore.RestoreInto` | да |
| Phone: уведомления | `CreateSnapshot()` / `PhoneNotificationsRestore.RestoreInto` | да |
| Phone: приложения и контакты | **API нет** — сохраняйте своим кодом или пересоздавайте | ограничение P1-9 |

### 4.2 Порядок восстановления

1. Кошелёк (баланс + журнал) — без него платежи и возвраты не имеют смысла.
2. Часы игры.
3. `ShopService` → `RestorePendingRefunds`.
4. `DebtService` → `RestoreSnapshot`; затем `RetryPendingRecovery()`.
5. `DeliveryService` (**новый экземпляр**) → `RestoreSnapshot`; затем `GetStatus`
   для каждого заказа / `Refresh` для активного.
6. Phone: `PhoneMessageService` и `PhoneNotificationService` → `RestoreInto`;
   затем `PhoneFacade.SyncMessageBadge()`.
7. Сверка: баланс, сумма истории платежей, сумма возвратов.

Восстановление **до** первого кадра геймплея: иначе UI успеет показать
состояние «новой игры».

### 4.3 Правила, которые нельзя нарушать

* Снимок Delivery восстанавливается **только на пустом** `DeliveryService`.
  Если заказы уже зарегистрированы кодом — сначала новый экземпляр.
* Снимок Debts нельзя применять, пока идёт списание (`InvalidState`) — не
  вызывайте загрузку из адаптера кошелька.
* Повреждённый снимок **не применяется** (все три валидатора возвращают
  ошибку и не меняют состояние). Показывайте игроку «сохранение повреждено»,
  не начинайте новую игру молча.
* Пишите сохранение атомарно (temp + rename) и храните предыдущий файл:
  версионирование схемы есть только у Debts (`SchemaVersion = 1`) и Delivery
  (`SchemaVersion = 1`).
* Не сохраняйте игру в момент, когда `ShopService.PendingRefundCount > 0` или
  `DebtService.PendingOperationCount > 0`, **если** не сохраняете
  соответствующие журналы. Лучше сохранять их всегда — иначе деньги теряются.

### 4.4 Что НЕ готово

Единой системы сохранений нет: нет общего файла мира, нет версионирования всех
снимков, нет снимков приложений/контактов Phone, нет автоматической сверки
кошелька с журналами. Всё перечисленное — работа проекта, а не модулей.

## 6. Минимальные задания для Codex

Каждое задание — отдельная задача с приёмкой. Не объединять.

**C-2. Прогон 259 тестов.**
Обернуть существующие `TestSuite`/`MiniTestRunner` в NUnit (`[Test]` на каждый
кейс) или подключить раннер как есть. Приёмка: отчёт с числом пройденных;
провалы не «глушить», а разбирать.

**C-3. Адаптер кошелька (Economy + Debts).**

* Не переписывать модули «под Unity» (MonoBehaviour, `Update`, `ScriptableObject`).
* Не добавлять в модули `using UnityEngine`.
