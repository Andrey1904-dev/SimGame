# Модуль долгов — LIFE FROM ZERO, ТЗ №016 / №016.2

Независимый C#-модуль «долги, кредиторы, платежи, просрочки, штрафы, стадии взыскания».
Unity 6000.3.27f1, C# 9. Без Unity API, без MonoBehaviour, без сторонних пакетов,
без Singleton. Сборка `LifeFromZero.Debts` (`noEngineReferences: true`).

Модуль **не зависит** от `Economy/`, `Jobs/Delivery/` и `Phone/` и не изменяет их.
Собственных `MoneyWallet`, `GameClock` и `PhoneFacade` внутри нет — только контракты
адаптеров, которые реализует интегрирующая сторона.

## Финансовые контракты (ТЗ №021)

* `DebtPaymentId` задаёт пространство `debt:` — идентификаторы платежей не пересекаются
  с `shop:`/`shop-refund:`/`delivery:` в общем журнале кошелька.
* Повтор `paymentId` идемпотентен: возвращается полный прежний результат (суммы и остаток)
  без списания и без второй записи в истории.
* Компенсация помечает платёж (`DebtPaymentRecord.Refunded`, поле `Refunded` в снимке):
  повтор с тем же `paymentId` после возврата денег отклоняется, а не зачитывается снова.
* `paymentId`, уже зачтённый по ДРУГОМУ долгу, отклоняется кодом `DuplicatePayment` без списания
  и без записи в историю второго долга (это конфликт ключей, а не повтор).
* Тесты: 97 (87 прежних + 10 в `DebtFinancialContractTests`), реально прогнаны вне Unity.

## Ключевые решения

### Деньги — только `long` рублей

Типы с плавающей точкой в денежных расчётах не используются. Вся арифметика идёт
через `DebtMath` (`TryAdd`, `TrySubtract`, `TryMultiply`, `TryPercent`) с проверкой
переполнения. Проценты задаются в **базисных пунктах** (100 б.п. = 1%), что исключает
дробные коэффициенты.

Раздельный учёт: `PrincipalRemaining` (основной долг), `PenaltiesRemaining`
(непогашенные штрафы), `PenaltiesAccrued` (начислено за всё время), `PaidTotal`
(выплачено), `TotalRemaining` (общая задолженность).

**Инварианты долга** (проверяются при создании и в валидаторе снимков):

* `PrincipalRemaining <= PrincipalOriginal`, `PenaltiesRemaining <= PenaltiesAccrued`;
* `PaidTotal == (PrincipalOriginal - PrincipalRemaining) + (PenaltiesAccrued - PenaltiesRemaining)`;
* `PrincipalOriginal + PenaltyMaxTotal` помещается в `long` — поэтому `TotalRemaining`
  и `PaidTotal` не могут переполниться в принципе;
* `Closed` ⟺ `TotalRemaining == 0`.

### Порядок погашения

**Сначала штрафы, затем основной долг.** Это явно заданное игровое правило модуля,
а не универсальная юридическая норма. Порядок реализован в единственном месте —
`DebtService.ApplyConfirmedPayment`.

### Процентная ставка

`InterestRateBasisPoints` — **разовая простая надбавка** к основному долгу при
создании (`principal + principal * bps / 10000`). Сложные проценты и периодическое
начисление процентов не моделируются; периодические начисления задаются политикой
штрафов. Это осознанное упрощение, зафиксированное в XML-документации
`DebtConfiguration`.

### Платёж: журнал намерения + идемпотентность

`TryPay(debtId, amount, paymentId)`:

1. Восстановление незавершённых операций; если журнал непуст — `PendingRecovery`.
2. Проверка ID долга → уникальности `paymentId` → суммы → состояния долга →
   отсутствия переплаты → возможности зачёта → баланса.
3. **Запись журнала намерения ДО списания.**
4. `IDebtWalletAdapter.TryDebit(paymentId, amount)`.
5. При `false`/исключении — уточнение исхода через `TryWasDebited`. Если списание
   было — платёж зачитывается; если не было — журнал снимается; если журнал адаптера
   недоступен — операция остаётся ждать, новые платежи блокируются.
6. Зачёт по **актуальному** состоянию долга, запись истории, освобождение журнала,
   рассылка событий.

Распределение суммы пересчитывается в момент зачёта, а не берётся из значений,
снятых до вызова адаптера — иначе реентрантный адаптер мог бы затереть начисления.
Журнал освобождается **до** рассылки событий — иначе обработчик, вызвавший
`CreateSnapshot()`, получил бы снимок, который валидатор отклоняет.
Пока списание «в полёте», вложенное восстановление не трогает текущую операцию.

### Штрафы и просрочки

Время — целые игровые минуты через `IDebtClockAdapter`. Просрочка начинается
**строго после** `DueAtMinutes + GracePeriodMinutes`. Периоды считаются от этого
момента: период 1 — минуты `1..PeriodMinutes` просрочки, период 2 — следующие
`PeriodMinutes` и т.д.

Штраф начисляется **один раз за расчётный период**: хранится `LastPenaltyPeriodIndex`,
поэтому повторный `UpdateTime()` в тот же момент (или в тот же период) ничего не
начисляет. Большие скачки времени начисляют все пропущенные периоды одним
начислением, ограниченным `MaxTotalRubles`; переполнение исключено делением
(`periodsToCharge > remainingCap / perPeriod`). Штрафы можно отключить для
отдельного долга (`PenaltyPolicy.Disabled`).

### Стадии взыскания

Стадия выводится из длительности просрочки и настраиваемых порогов
(`CollectionThresholds`, по умолчанию 3 / 14 / 30 игровых суток). Стадия только
повышается; после полного погашения — `Closed`. Модуль **только сообщает** о
наступлении стадии: NPC-коллекторов, суда, ареста имущества и угроз нет.

### События

8 типов: `DebtCreated`, `PaymentCompleted`, `PaymentRejected`, `PaymentDue`,
`DebtOverdue`, `PenaltyApplied`, `CollectionStageChanged`, `DebtClosed`.
Одноразовые события (`PaymentDue`, `DebtOverdue`, `DebtClosed`) защищены флагами,
которые сохраняются в снимке. Сбой обработчика перехватывается и **не отменяет**
подтверждённый платёж. `DebtEventHub` даёт подписку нескольких систем с изоляцией
сбоев.

### Сохранение

`CreateSnapshot()` / `RestoreSnapshot(snapshot)`. Снимок — плоские DTO-массивы
с публичными полями и `[Serializable]`, без словарей и интерфейсов, поэтому
пригоден для `JsonUtility`. Сохраняются долги, кредиторы, суммы, сроки, стадии,
история платежей с их ID, последние периоды начисления штрафов, флаги одноразовых
событий и журнал незавершённых операций.

Валидация выполняется **целиком до применения**: повреждённый снимок не меняет
рабочее состояние. Проверяются ссылки, уникальность ID, неотрицательность,
финансовые инварианты и согласованность истории платежей с остатками.

## Стартовые условия игры

Главный герой начинает с наличными 1 270 ₽, общим долгом 38 400 ₽, квартирой №67
и без стабильной работы. Модуль долгов отвечает **только за долг**: наличчные —
зона кошелька, квартира — зона жилья.

Стартовый долг создаётся **данными**, а не логикой сервиса:

```csharp
StartingDebtScenario scenario = StartingDebtFactory.Create(
    creditorId: "creditor-1",
    creditorName: "Кредитор",          // настраивается
    dueAtMinutes: 30L * 1440L,         // настраивается
    interestRateBasisPoints: 0,        // настраивается
    gracePeriodMinutes: 3L * 1440L);

service.RegisterCreditor(scenario.Creditor);
service.CreateDebt(scenario.Debt);     // 38 400 ₽
```

`DebtService` не содержит стартовых сумм. Обязательные сюжетные факты не задаются.
