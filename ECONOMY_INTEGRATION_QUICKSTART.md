# Economy: короткая инструкция подключения (ТЗ №021)

Кратко и по делу: что уже готово в коде, что Codex обязан реализовать в своих компонентах
и где проходят границы гарантий. Полные контракты — в XML-комментариях исходников и в
`Economy/INTEGRATION.md`; здесь только порядок действий.

---

## 0. Главное

* Логика покупки **готова**: `Economy/Shop/ShopService.cs`. Проектировать финансовые
  контракты не нужно — они уже есть (`ShopOperation`, `ShopOperationState`,
  `FinancialOperationId`, `IIdempotentWalletAdapter`, `IIdempotentInventoryAdapter`).
* Codex пишет **два адаптера** поверх существующих `MoneyWallet` и `FoodInventory`
  и связывает их с магазином. Всё остальное — вызовы и UI.
* Есть два честно разделённых режима. **Режим A** можно включать сразу. **Режим B**
  нельзя объявлять готовым без реальных журналов в кошельке/инвентаре и согласованной
  фиксации сохранения.

---

## 1. Порядок подключения (Режим A)

```csharp
// 1. Адаптер кошелька по СТАРОМУ контракту (IWalletAdapter): Balance / TrySpend / TryRefund.
//    Оборачиваем в LegacyWalletAdapter — он защищает от повтора ВНУТРИ сессии.
IWalletAdapter wallet = new LegacyWalletAdapter(new MoneyWalletAdapter(moneyWallet));

// 2. Адаптер инвентаря по старому контракту (IInventoryAdapter): CanApprove / TryAdd.
IInventoryAdapter inventory = new FoodInventoryAdapter(foodInventory);

// 3. Сервис магазина — один экземпляр на игру, живёт в сессии.
var shop = new ShopService(ShopCatalog.CreateDefault());

// 4. Покупка всегда с идентификатором. Идентификатор создаётся ОДИН РАЗ на попытку
//    и переиспользуется при повторе (обрыв, отказ, повторный клик).
string purchaseId = "buy-" + System.Guid.NewGuid().ToString("N");
PurchaseResult result = shop.Purchase(wallet, inventory, new PurchaseRequest("bread", 1), purchaseId);

// 5. Повтор той же покупки (тот же purchaseId) безопасен: result.IsReplay == true,
//    деньги и товар не двигаются.
```

Минимальные требования к адаптерам:

| Адаптер | Метод | Требование |
|---|---|---|
| `MoneyWalletAdapter` | `Balance` | чтение без побочных эффектов и исключений |
| | `TrySpend(Money)` | атомарно: либо вся сумма, либо ничего; при `false` баланс не изменён |
| | `TryRefund(Money)` | возвращает ровно списанную сумму |
| `FoodInventoryAdapter` | `CanApprove(itemId, qty)` | проверка вместимости **без изменения** состояния |
| | `TryAdd(itemId, qty)` | при `false` состояние не изменено (никакой частичной выдачи) |

Ошибки адаптеров не пробрасываются в UI: сервис превращает их в коды
(`InternalError`, `InventoryRejected`, `OutcomeUnknown`, `PendingOperation`).
Логирование — задача адаптера.

### Что делает Режим A

| Гарантия | Есть? |
|---|---|
| Повтор с тем же `purchaseId` внутри сессии не списывает и не выдаёт повторно | **да** |
| Недостаток средств не приводит к выдаче товара | **да** |
| Исключение обработчика `Changed` не отменяет покупку | **да** |
| Сбой инвентаря после списания → деньги возвращаются | **да** |
| Сбой кошелька с неизвестным исходом не превращается в «денег нет» (`OutcomeUnknown`) | **да** |
| Новые покупки блокируются, пока висит незавершённая операция | **да** |
| Переживание аварийного завершения игры | **нет** |
| Повтор после перезапуска без журнала кошелька | **нет** (честный `OutcomeUnknown`) |

## 2. Режим B (сохранения): чего не хватает

Чтобы объявить Режим B готовым, нужны **одновременно** три вещи, и все три — на стороне
интеграции, а не в этом репозитории:

1. **Кошелёк** реализует `IIdempotentWalletAdapter` с `IsDurable == true`
   (журнал `operationId → исход` в сохранении).
2. **Инвентарь** реализует `IIdempotentInventoryAdapter` с `IsDurable == true`
   (журнал выдачи `operationId → выдано/отклонено`).
3. **Согласованная фиксация**: журнал магазина (`ShopService.CreateSnapshot()`), баланс
   кошелька и содержимое инвентаря сохраняются **в одной записи сохранения**. Если
   сохранять их по отдельности, между записями возможен сбой, и деньги/товар разойдутся.

Пока этого нет:

* `ShopService.IsDurable(wallet)` возвращает `false`;
* после загрузки «висящая» операция либо доигрывается по журналам адаптеров, либо
  остаётся видимой и блокирует новые покупки — выдуманного исхода нет.

Снимок магазина уже готов и не требует доработки:

```csharp
ShopSnapshot snapshot = shop.CreateSnapshot();      // сериализуйте вместе с кошельком/инвентарём
shop.RestoreSnapshot(snapshot, out string error);   // на свежем сервисе при загрузке
shop.RetryPendingOperations(wallet, inventory);     // доводит/компенсирует незавершённые
```

Формат файла выбирает Codex: DTO плоские (`[Serializable]`, публичные поля), поэтому
подходят и Unity `JsonUtility`, и `System.Text.Json`.

## 3. Коды результата

| Код | Значение | Что делать UI/вызывающему |
|---|---|---|
| `Success` | покупка выполнена | товар уже в инвентаре |
| `InsufficientFunds` | денег не хватает | сообщение игроку |
| `ProductNotFound` | нет такого товара | ошибка контента |
| `InvalidQuantity` | плохое количество/переполнение | ошибка вызова |
| `InventoryRejected` | инвентарь не принял товар | деньги возвращены |
| `InvalidArgument` | некорректный `purchaseId` | ошибка вызова |
| `InternalError` | отказ адаптера, деньги не изменены **или** возврат не удался | сверить баланс |
| `PendingRefund` | висит незавершённый возврат | подождать/повторить восстановление |
| `PendingOperation` | висит незавершённая покупка | не начинать новую |
| `OutcomeUnknown` | исход неизвестен | повторить с тем же `purchaseId` позже |

`PurchaseResult.IsReplay == true` означает «это ответ на повтор, сейчас ничего не менялось».
`PurchaseResult.PurchaseId` — идентификатор, под которым операция записана в журнал.

## 4. Событие `Changed`

```csharp
shop.Changed += operation => UpdateShopUi(operation.State, operation.PurchaseId);
```

* возникает после фиксации состояния (`Debited`, `Granted`, `Declined`, `RefundPending`, …);
* исключение обработчика проглатывается — финансовый результат не зависит от UI;
* внутри обработчика **нельзя** начинать новую покупку: сервис отклонит её кодом
  `PendingOperation` (защита от повторного входа);
* при `RestoreSnapshot` событие не возникает (это загрузка, а не gameplay).

---

## 5. Что проверить в Unity (обязательный минимум)

1. `MoneyWalletAdapter.TrySpend` **атомарен** и не списывает половину суммы.
2. `FoodInventoryAdapter.CanApprove` действительно не мутирует инвентарь (иначе деньги
   спишутся при полном инвентаре и вернутся только компенсацией).
3. `TryAdd` при `false` не добавляет товар частично.
4. Повторный вызов `ShopService.Purchase` с тем же `purchaseId` не выдаёт второй хлеб.
5. Исключение в обработчике `Changed` не ломает покупку.
6. Сохранение/загрузка: `CreateSnapshot` → `RestoreSnapshot` → `RetryPendingOperations`
   не возвращает деньги дважды.
