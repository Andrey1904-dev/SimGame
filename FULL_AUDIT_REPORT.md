## 2. Что реально запускалось (методика)

`dotnet`/`csc`/`mcs`/`mono`/`msbuild` недоступны, поэтому написаны два статических
анализатора **вне репозитория** (`/tmp/analyze.js`, `/tmp/deep.js`, в Git не попадают,
Node.js). Они не заменяют компилятор; они находят конкретный класс ошибок.

**`analyze.js`** (структура, 102 файла):

* баланс `{}`/`()` во всех файлах;
* отсутствие конструкций C# 10+: file-scoped namespace, `record struct`,
  `global using`, `required`, raw strings, `static abstract`, `scoped`, `file`-типы;
* каждый `using` разрешается в объявленный namespace (иначе CS0246);
* изоляция модулей: ни один модуль не использует namespace другого модуля;
* дубли типов (namespace + имя + арность) внутри сборки;
* Unity API (`MonoBehaviour`, `GameObject`, `UnityEngine*`, `Debug.Log`, …)
  в сборках с `noEngineReferences: true`;
* валидность JSON всех `.asmdef` и разрешимость ссылок между сборками;
* покрытие каждого `.cs` ровно одной asmdef;
* регистрация тестов: `suite.Add("…", Method)` → метод существует.

**`deep.js`** (контракты):

* реализация интерфейсов: каждый класс/структура объявляет все члены интерфейса
  (25 интерфейсов, 29 реализаций — расхождений нет);
* арность конструкторов: каждый `new X(...)` соответствует объявленному ctor;
* существование статических членов: каждый `Type.Member` объявлен в типе.

**Результат:** 0 структурных ошибок. Из `deep.js` остались только 2 находки,
которые я проверил вручную и признал ложными срабатываниями:
`scenario.Debt.PrincipalRubles` / `scenario.Debt.DebtId` — `Debt` здесь не тип
`LifeFromZero.Debts.Core.Debt`, а свойство `StartingDebtScenario.Debt`
типа `DebtConfiguration`.

**Чего эта методика не проверяет (и не должна считаться проверкой):** перегрузку
методов, обобщённые ограничения, вывод типов, неявные преобразования, доступность
`internal`, порядок объявлений, инициализацию `readonly` полей, фактическое
поведение. Это остаётся на компилятор и EditMode-тесты в Unity.

## 3. Находки по модулям (сводка)

### 3.1 Economy

Проверено: целочисленная арифметика (`Money` — `long`, все операции с проверкой
переполнения), запрет отрицательных сумм (`FromRubles` бросает,
`TryFromRubles` возвращает `false`), покупка при недостатке средств, отказ
инвентаря до и после списания, возврат денег, журнал незавершённых возвратов,
повторное выполнение операций, исключения адаптеров (`SafeCall`), инвариант
«деньги списаны ровно тогда, когда товар выдан».

Порядок операций корректен: `CanApprove` (без мутации) → `TrySpend` → `TryAdd`,
и любой сбой после списания проходит через `Compensate`. Потерять деньги при
отказе инвентаря нельзя: сумма попадает в `_pendingRefunds` и повторяется.
Пока журнал непуст, новые покупки блокируются кодом `PendingRefund` — это
правильно, иначе игрок потратил бы уже возвращённые деньги.

Найдено: журнал незавершённых возвратов жил только в памяти (**P1-1**, исправлено),
две неточности в кодах ответа (**P2-1**, **P2-2**).

### 3.2 Delivery

Проверено: все переходы (`Available → Accepted → PickedUp → Completed`,
`Cancelled`, `Failed`), приём, получение груза, доставка, отмена, отказ,
просрочка, выплата, повторное завершение, один активный заказ, ошибки часов
(NaN/∞/исключение), ошибки геолокации, исключения платёжного адаптера.

Ключевой инвариант выполнен: состояние переходит в `Completed` **только после**
успешного `TryCredit`; при отказе заказ остаётся в `PickedUp` и работу можно
завершить позже; флаг `PayoutGranted` не даёт начислить дважды.

Найдено: **у модуля не было сохранения состояния** (**P0-1**, исправлено),
статус несуществующего заказа сообщал `Available` (**P1-5**, исправлено),
противоречивое описание `Cancel` в интерфейсе (**P2-3**),
у `IPayoutAdapter` нет ключа идемпотентности (**P1-7**, открыто, см. §8).

### 3.3 Phone

Проверено: контакты (`PhoneBook`: дубликаты, поиск по имени/подстроке,
неоднозначное имя), сообщения (`PhoneMessageService`: создание переписки,
отправка, приём, история, прочтение, идемпотентность, восстановление ID),
уведомления (дедупликация по ID, типы, каналы, `MarkAllRead`), счётчики
непрочитанного (`int` с защитой от переполнения), регистрация приложений,
исключения обработчиков (`PhoneNotificationHub.FailSafeAddUnread`,
`SafeAdapter`-подобные обёртки в интеграциях), snapshot/restore сообщений и
уведомлений, защита снимков от изменения извне (defensive copy + read-only),
пустые и некорректные данные (пустые ID/тексты, null-элементы от источников,
неизвестный тип уведомления, исходящее «непрочитанным»).

**Ранее отмеченный риск подтверждён:** доставка через `IPhoneInbox`
увеличивала счётчик переписки (`TotalUnread`), но **бейдж приложения
`messages` не менялся вообще**. Причина архитектурная: у сервиса сообщений нет
и не должно быть ссылки на реестр приложений. Исправлено через явную
идемпотентную синхронизацию (**P1-2**), а не через «+1 в Inbox», потому что
`+1` давал бы двойной счёт при `Push` с каналом `AppBadge`.

Найдено: бейдж (**P1-2**, исправлено), `DebtDto` без статуса (**P1-3**,
исправлено). Открыто: у `PhoneAppRegistry` и `PhoneBook` нет снимков (**P1-9**,
см. §7).

### 3.4 Debts

Проверено: создание долгов и кредиторов (дубликаты, неизвестный кредитор,
неположительная сумма, отрицательные сроки, переполнение «основной + процент»),
стартовая задолженность **38 400 ₽** (`StartingDebtFactory.StartingDebtRubles =
38400L`, это данные, а не логика сервиса), частичные и полные платежи, защита
от двойного списания (`paymentId` в истории **и** в журнале), порядок погашения
**штрафы → основной долг** (`penaltyPart = min(amount, PenaltiesRemaining)`),
штрафы и лимит начислений (`PenaltyCalculator` + `MaxTotalRubles`), просрочки и
стадии взыскания (3/14/30 суток), большие скачки времени (индекс периода
считается без переполнения, лишние периоды за один вызов), повторные вызовы
через адаптеры (реентрантность), журнал платежей, восстановление после сбоя,
сохранение/загрузка, корректность событий.

Проверка трёх ранее исправленных проблем — **все три держатся**:

1. **Штрафы не теряются во время списания.** Распределение платежа считается
   заново по актуальному состоянию в `ApplyConfirmedPayment`, а не по значениям,
   снятым до `TryDebit`. Реентрантный `UpdateTime` внутри списания не затирается
   (тест `ReentrantPenaltiesNotLost`).
2. **Снимок внутри `DebtClosed` не противоречив.** `_pending.Remove(operation)`
   выполняется **до** рассылки `CollectionStageChanged`/`DebtClosed`/
   `PaymentCompleted`, поэтому `paymentId` не может одновременно быть в истории
   и в журнале (тест `SnapshotInsideClosedEventValid`).
3. **Вложенное восстановление не отменяет текущий платёж.** `_inDebitWindow`
   блокирует `ResolvePending`, пока списание «в полёте» (тест
   `ReentrantRecoveryKeepsJournal`).

Найдено: восстановление снимка во время списания портило состояние (**P1-4**,
исправлено); валидатор отклонял снимки, которые сервис создаёт сам (**P1-6**,
исправлено).

## 4. Найденные дефекты и исправления

### P0 — потеря денег / дублирование выплат / повреждение сохранений

**P0-1. Delivery: состояние заказов не сохранялось → повторная выплата после загрузки.**
`DeliveryService` хранил `State`, метки времени и `PayoutGranted` только в памяти,
публичного снимка не было. Достаточно было сохранить игру после выполненного
заказа: после загрузки заказ снова `Available`, его принимают, завершают и
**платят второй раз**. Модуль долгов такую защиту имел, доставка — нет.
*Исправление:* `Jobs/Delivery/DeliverySnapshot.cs` (+ `DeliverySnapshotValidator`)
и `DeliveryService.CreateSnapshot()/RestoreSnapshot(snapshot, out error)`.
Валидатор проверяет уникальность ID, диапазон состояний, согласованность меток
времени, **`PayoutGranted == (State == Completed)`** и «не более одного активного
заказа». Восстановление атомарно и разрешено только на пустом сервисе.
*Проверка:* 4 регрессионных теста (в т.ч. «оплата не продублирована после загрузки»).

### P1 — неправильная логика / ошибки интеграции

**P1-1. Economy: журнал незавершённых возвратов не сохранялся.**
Если `TryRefund` отказал (а это единственный путь, на котором деньги «висят»
вне кошелька), запись жила только в объекте `ShopService`. Сохранение и загрузка
уничтожали её — игрок терял уже списанные деньги окончательно.
*Исправление:* `ShopService.PendingRefunds` (read-only) и
`RestorePendingRefunds(IEnumerable<Money>)`. Контракт `IShopService` не изменён.
*Проверка:* тест полного цикла save → load → блокировка покупок → возврат.

**P1-2. Phone: бейдж приложения «Сообщения» не обновлялся при доставке через Inbox.**
Подтверждение ранее отмеченного риска.
*Исправление:* `Phone/Integrations/PhoneBadgeSync.cs` —
`SyncMessagesBadge(apps, messages)` **устанавливает** бейдж равным
`TotalUnread` (сброс + точное значение), поэтому операция идемпотентна и не
накручивается; `PhoneFacade.SyncMessageBadge()` для удобства.
Автоматического `+1` в `Inbox` намеренно нет: `Push` с каналом `AppBadge`
дал бы +2 за одно событие. **Ограничение:** синхронизацию должен вызвать
интегратор (после доставки или при открытии экрана); это записано в
`UNITY_INTEGRATION_PLAN.md`.
*Проверка:* 2 теста (в т.ч. «пять вызовов не накручивают счётчик»).

**P1-3. Phone ↔ Debts: телефон не мог показать стадию долга.**
`DebtDto` содержал только `Id`, `Title`, `AmountRubles`, `DueAtMinutes`.
Требование ТЗ «видны остатки, сроки **и статусы**» невыполнимо.
*Исправление:* `DebtPhase` (Unknown/Current/Overdue/Reminder/Collection/
LegalAction/Closed) и свойство `DebtDto.Phase`. Старый 4-аргументный
конструктор сохранён и даёт `Unknown` — существующий код не ломается.
*Проверка:* тест «список долгов отдаёт стадию взыскания».

**P1-4. Debts: `RestoreSnapshot` во время незавершённого списания.**
Если загрузка выполнялась, пока `TryDebit` ещё не вернулся, словарь долгов
подменялся, и зачёт текущего платежа применялся к объекту `Debt`, которого в
сервисе уже нет: деньги списаны, остаток не уменьшен, история платежей есть.
Следующий снимок становился противоречивым.
*Исправление:* `RestoreSnapshot` отклоняется кодом `InvalidState`, пока
`_inDebitWindow`.
*Проверка:* тест с реентрантным кошельком (`RestoreDuringDebitRejected`).

**P1-5. Delivery: статус несуществующего заказа сообщал `Available`.**
`NotFoundStatus()` возвращал `State = Available` с `OrderId = null`, что прямо
противоречило собственному документу класса («фантомного состояния Available у
несуществующего заказа нет»). UI или адаптер телефона могли нарисовать
несуществующий заказ как доступный к принятию.
*Исправление:* добавлено `DeliveryOrderState.None = 6` (значение в конце enum,
существующие значения не сдвинуты), `NotFoundStatus()` использует его.
*Проверка:* тест `NotFoundIsNotAvailable`.

**P1-6. Debts: валидатор отклонял снимки, которые сервис создаёт сам.**
Проверка «сумма незавершённой операции не больше задолженности» применялась ко
всем фазам. Но в фазах `DebitConfirmed`/`RefundPending` деньги **уже списаны**,
сумма стала фактом, а долг за это время мог уменьшиться (например, долг закрыли,
пока списание было «в полёте»). Такой снимок сервис формирует сам, а валидатор
его отклонял — сохранение становилось незагружаемым **вместе с единственной
записью о деньгах, которые надо вернуть**.
*Исправление:* проверка ограничена фазой `DebitPending`; для остальных
действует `AmountRubles > 0` и существование долга.
*Проверка:* существующий тест `PendingTooLarge` (фаза 0) сохранён, добавлен
тест `RefundPendingAboveRemaining`.

### P2 — незначительные

**P2-1. Economy: `InsufficientFunds` при отказе кошелька по другой причине.**
`TrySpend == false` трактуется как «недостаточно денег», даже если баланс был
достаточен (адаптер отказал по своей причине). Код ответа вводит в заблуждение,
но состояние корректно: деньги не списаны. Не исправлял: это потребовало бы
нового значения `EconomyResultCode` (изменение публичного контракта ради
диагностики).

**P2-2. Economy: `InternalError` при отложенном возврате.**
Когда возврат ушёл в журнал, вызывающий получает `InternalError` и не может
отличить «внутреннюю ошибку» от «деньги в пути». Фактическое состояние видно
через `PendingRefundCount`/`PendingRefunds`. Оставлено сознательно: менять
код ответа — контракт.

**P2-3. Delivery: противоречивое описание `IDeliveryService.Cancel`.**
«Отменяет заказ: доступный, принятый или полученный. После груза отмена
запрещена» — вторая фраза отменяет первую. Код прав (после `PickedUp` отмена
запрещена), текст — нет.

**P2-4. Документация:** корневой `README.md` не упоминает модуль долгов и
содержит устаревшие счётчики тестов (33/40/90). Модульные `README.md` —
тоже (это снимок на момент ТЗ №015).

**P2-5. Delivery: снимок есть только у класса, не у `IDeliveryService`.**
Сделано намеренно: добавление членов в интерфейс сломало бы сторонние
реализации. Интегратору нужно держать ссылку на `DeliveryService`.

**P2-6. Phone: `DebtDto.DueAtMinutes` — `double` с сентинелом `-1`,**
тогда как модуль долгов использует `long` без сентинела. Адаптер обязан
явно отображать; легко перепутать «нет срока» и «срок 0».

## 5. Сквозной аудит интеграции

Проверялось по контрактам, без создания поддельных Unity-адаптеров.

### Economy ↔ Delivery

| Требование | Факт |
|---|---|
| Выплата курьеру поступает в кошелёк | Возможно: `IPayoutAdapter.TryCredit(long)`. Но **у `IWalletAdapter` нет операции начисления** — только `TrySpend`/`TryRefund`. Начисление обязан реализовать адаптер поверх настоящего `MoneyWallet`. Это не дефект, а осознанная граница: Economy не владеет кошельком. |
| Повторная доставка не создаёт повторную выплату | В рамках сессии — гарантировано (`PayoutGranted`, состояние `Completed`). **После загрузки** — гарантировано только с P0-1 (снимок), который добавлен. |
| Ошибка начисления не уничтожает информацию о выполненной работе | Заказ остаётся `PickedUp`, `Complete` можно повторить. Остаётся оговорка: если после неудачной выплаты игровое время перешло за дедлайн, повторный `Complete` провалит заказ (`DeadlineExpired`) — работа не оплачивается. Это игровое правило, а не дефект, но знать о нём надо. |

### Economy ↔ Debts

| Требование | Факт |
|---|---|
| Оплата долга списывает деньги ровно один раз | `IDebtWalletAdapter.TryDebit(paymentId, …)` идемпотентен по контракту; сервис дополнительно ведёт историю + журнал. |
| Конфликтов между возвратами магазина и платежами по долгам нет | Оба пути работают через один `MoneyWallet`; магазин делает `TrySpend/TryRefund` без ID, долги — `TryDebit/TryRefund(paymentId)`. Конфликта **по смыслу** нет, но и **согласованности нет**: это два независимых журнала. |
| ID финансовых операций не пересекаются | **У Economy идентификаторов операций нет вообще.** У долгов `paymentId` уникален только внутри сервиса долгов. → Адаптер кошелька обязан сам вводить пространство имён (например, префикс `debt:`), иначе `paymentId` долга может совпасть с идентификатором другой системы в журнале адаптера. |
| Баланс не становится отрицательным | Обе системы проверяют баланс **до** операции, но окончательная защита — на адаптере: и `TrySpend`, и `TryDebit` обязаны отклонять списание больше баланса. |

### Phone ↔ Delivery

| Требование | Факт |
|---|---|
| Телефон может отображать активный заказ | `IDeliveryJobsSource.TryGetOrders/TryGetActiveOrderId` + `WorkSummaryService` (только чтение, исключения гасятся). |
| Статусы обновляются корректно | `DeliveryJobPhase` (Phone) 1:1 соответствует `DeliveryOrderState` (Delivery) по именам и по номерам 0–5. Адаптер должен **отображать явно**, а не приводить `int`: у Delivery появилось значение `None = 6`, у Phone его нет — прямое приведение теперь даст неизвестную фазу. |
| Нет обязательных прямых зависимостей от Unity | Ни один модуль не ссылается на Unity (`noEngineReferences: true`, 0 вхождений Unity API). |

### Phone ↔ Debts

| Требование | Факт |
|---|---|
| Телефон может отображать список долгов | `IDebtsSource.TryGetDebts` → `BankSummaryService`; null-элементы фильтруются, исключения гасятся. |
| Видны остатки, сроки и статусы | Остатки и сроки — были; **статус отсутствовал** (P1-3, исправлено). |

Отдельные сценарии из ТЗ:

* **Повторная загрузка одного сохранения** — снимки не мутируют состояние при
  создании (defensive copy в Phone; новые массивы в Debts/Delivery), поэтому
  повторная загрузка даёт то же состояние. Для Delivery восстановление запрещено
  поверх непустого сервиса — повторная загрузка требует нового экземпляра.
* **Незавершённая покупка** — «зависший» возврат сохраняется через
  `PendingRefunds` (P1-1) и продолжает блокировать покупки после загрузки.
* **Незавершённая выплата** — теперь сохраняется через `DeliverySnapshot`
  (`PickedUp` + `PayoutGranted = false`) и завершается после загрузки.
* **Незавершённый платёж по долгу** — `PendingOperations` в снимке, восстановление
  в `TryPay`/`RetryPendingRecovery` по журналу кошелька.
* **Согласованность кошелька и журналов** — модули её **не проверяют**: кошелёк
  вне их ответственности. Сверка баланса с историей платежей/возвратов — задача
  интегратора (см. план).
* **Очерёдность восстановления** — в `UNITY_INTEGRATION_PLAN.md` §5.

**Глобальная система сохранений НЕ готова.** Готовы четыре независимых набора
снимков; нет: (а) версионирования формата файла, (б) атомарной записи на диск,
(в) снимков приложений/контактов Phone, (г) единого снимка мира и порядка
восстановления в коде.

## 8. Оставшиеся риски (не исправлено)

1. **P1-7. У выплаты нет ключа идемпотентности.** `IPayoutAdapter.TryCredit(long)`
   не принимает идентификатор заказа/операции. Если игра упадёт между
   начислением и записью сохранения, повторное завершение заказа начислит
   деньги второй раз. Снимок (P0-1) сокращает окно, но не закрывает его.
   *Что делать:* адаптер `TryCredit` должен быть идемпотентным по заказу
   (журнал начислений в `MoneyWallet`), либо начисление должно идти через
   `TryDebit`-подобный API с ID. Изменение контракта — за рамками аудита,
   потому что затронет все вызовы и Unity-адаптер.
2. **P1-9. Phone: нет снимков приложений и контактов.** Бейджи и книга контактов
   не переживают загрузку.
3. **P2-1/P2-2.** Неточные коды ответа Economy (см. §4).
4. **Раздельные журналы кошелька.** Economy и Debts не имеют общего источника
   истины по операциям; согласованность обеспечивается только адаптером.
5. **Дедлайн и неудачная выплата.** Просроченный заказ после сбоя выплаты
   проваливается — выполненная работа не оплачивается (правило, но спорное).
6. **Статический анализ ≠ выполнение.** Ни один тест не исполнялся; любая
   ошибка времени выполнения (в первую очередь в новом коде снимков Delivery)
   ещё не исключена.
