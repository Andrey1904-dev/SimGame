# Отчёт: можно ли использовать `Map.PNG` как подложку карты (ТЗ №042)

**Ответ: нет.** `Map.PNG` — стилизованный рисунок, а не план района в постоянном
масштабе. Даже лучшая честная модель привязки (гомография, МНК по 18 контрольным
точкам)
даёт **медианную ошибку 69.3 px ≈ 44.4 м** при допуске 12 px (7.7 м), и в допуск
попадает **1 точка из 18**. Максимум — **151.8 px ≈ 97 м** на точке `player.home`.

Поэтому карта в игре строится **из данных района** (`QuarterPlan`), а картинка
остаётся референсом для сверки. Цифры ниже зафиксированы тестом: попытка «улучшить»
привязку подгонкой контрольных точек немедленно уронит сборку.

---

## 1. Измерения (воспроизводимые)

| Модель привязки | В допуске 12 px | Медиана | Максимум | Худшая точка |
|---|---|---|---|---|
| Ортогональная (`District750Ortho`) | 1 / 18 | 108.4 px (69.3 м) | 233.8 px (Мэрия) | `com-city-hall` |
| Подобие + поворот (`FitSimilarity`) | 0 / 18 | 126.1 px (80.7 м) | 206.0 px | `com-mall` |
| **Гомография, МНК** (`FitReferencePerspective`) | **1 / 18** | **69.3 px (44.4 м)** | **151.8 px** | `player.home (bld-n3)` |

Пересчёт: 1 px = 1 / 1.5627 м ≈ 0.64 м (`ReferenceRegionWidth = 1172 px` на 750 м).

## 2. Почему подгонка запрещена

* При ошибке 44 м маркер игрока показывал бы чужой квартал, а нарисованные улицы
  не совпадали бы с маршрутом (маршрут считается по настоящему графу дорог).
* Подгонка «до красивых цифр» требует двигать контрольные точки, то есть врать в
  данных. Это скрывает дефект, а не исправляет его.
* Смена сида/генератора обесценила бы подгонку молча.

## 3. Что сделано вместо подложки

```
QuarterPlan (данные района)                    ← единственный источник истины
  └─ UI/Core/QuarterPlanAdapter.Build()
       ├─ дороги → MapRoadSegment[]            (улицы и дворовые проезды различаются)
       ├─ точки  → MapPoiMarker[]              (район + 46 точек доставки)
       └─ граф   → RoadGraphData (59 узлов, 82 ребра, связный)
            └─ NavigationService               ← один маршрут для карты и HUD
```

* Рисуется один меш (`UI/Runtime/MapCanvasGraphic.cs`), а не сотни `Image`.
* Привязка мира к UV — `District750Ortho()`: `(0,0)→(0,0)`, `(750,750)→(1,1)`.
* `District750Perspective()` оставлена **только** для отчёта и диагностики; в
  отрисовке не участвует (тест «привязка к Map.PNG … расхождение зафиксировано»).

Попутно исправлен настоящий дефект: привязка шла только к перекрёсткам, и 17 из
46 адресов доставки (подъезды во дворах, 47–75 м до дороги) вообще не
маршрутизировались. Теперь привязка идёт к ближайшему **ребру**
(`RoadGraphData.FindNearestEdge`, `RoutePlanner.SnapToNetwork`), последний участок
— подход пешком (`RoutePath.EndsOnApproach`). Тест «все точки доставки District750
достижимы» это стережёт.

## 4. Что карта по-прежнему не делает (и почему)

| Не делает | Причина |
|---|---|
| Клик по карте не строит маршрут | в игре нет координат клика по миру; придумывать их — врать игроку |
| Нет «домов» и кварталов с `Map.PNG` | геометрия рисунка не совпадает с планом (§1) |
| Нет полигонов зданий | из `QuarterPlan` их нельзя получить без аппроксимации; рисуются POI-точки |
| Нет перетаскивания/зума с инерцией | не требуется сценарием; карта вписана в экран телефона |

## 5. Воспроизведение цифр

```bash
dotnet run --project UI/Tests/Console.csproj
```

Тесты, фиксирующие факты:

* «Карта: привязка к Map.PNG измерена и расхождение зафиксировано, а не скрыто» —
  медиана > 20 px и > 10 м, `IsAcceptable == false`.
* «Карта: ортогональная модель описывает Map.PNG не лучше перспективной».
* «Карта: гомография решается МНК и обратима».
* «Карта: подгонка подобия не превращается в „идеал“».

Если картинку когда-нибудь заменят на настоящий ортогональный план — эти тесты
упадут, и это правильный сигнал: тогда и `ReferenceHomography`, и отчёт
пересчитываются заново.
