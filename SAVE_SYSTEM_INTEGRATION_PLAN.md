# План сохранения (глобальный Save System не реализован)

Существуют `DeliverySnapshot` (заказы, стадии, время, PayoutGranted), `DebtSnapshot` (кредиторы, долги, штрафы, история и pending), `PhoneMessagesSnapshot`, `PhoneNotificationsSnapshot`, новые `PhoneAppsSnapshot` (в т.ч. availability/badges) и `PhoneBookSnapshot` (контакты); Economy хранит лишь суммы `PendingRefunds`, не ID или инвентарь. Кошелёк/инвентарь/время принадлежат игре, не дублировать в Phone. Бейдж сообщений производный: после restore выполнить SyncMessageBadge.

До записи: остановить финансовые операции, восстановить pending или надёжно записать их, получить устойчивый журнал кошелька, снимки всех модулей одного поколения и игровое время; создать envelope с версией схемы и save-lineage ID, поколением, checksum, затем атомарно опубликовать поколение с backup. Проверить сериализацию DTO round-trip: immutable DTO Phone не гарантированно поддерживаются JsonUtility. Код систем хранения неизвестен: NEEDS_UNITY_INSPECTION. При денежных операциях одного снимка недостаточно — нужен WAL/транзакция и reconciliation на стороне авторитетного кошелька.

Восстановление: проверить envelope, checksum, версии и все снимки во временных сервисах; восстановить кошелёк/журнал и часы, затем Economy pending, Delivery на пустой сервис, Debts на новый сервис согласно его валидатору, Phone snapshots и вычисляемые бейджи. Восстановить pending долгов по устойчивому журналу, сверить выплаты. Только после общего успеха атомарно заменить живые ссылки; при ошибке не публиковать ни один модуль, откатиться на предыдущее согласованное поколение или остановиться. Не создавать дефолтные заказы до restore. API и сериализация требуют Unity-проверки.

Сценарии:
1. Крах после выплаты: повторить с тем же ID через durable wallet. Если просрочен заказ при повторе, `Complete` может отказать до проверки кошелька: нужна reconciliation, не считать автоматическим восстановлением. Старые выплаты без ID требуют миграции вручную; повтор заблокировать до сверки.
2. Крах при платеже долга: durable `TryWasDebited`, pending и `RetryPendingRecovery`; без сохранённого pending до debit и журнала нельзя гарантировать согласованность.
3. Повреждение: отклонить всё, backup/ошибка, не частичное восстановление.
4. Один модуль восстановился, другой нет: только staged экземпляры, не менять живые; сохранить старое поколение.
5. Повтор загрузки: проверка поколения и журнала; не повторять финансовый эффект. Повтор phone restore детерминирован; Delivery требует нового пустого сервиса.
6. Старый формат: явная миграция и проверки, неподдерживаемую версию отклонить; не предполагать наличие ID у исторических операций.

Economy не имеет ID покупки/возврата и не может обеспечить идемпотентность через сбой; остановить интеграцию финансов до спроектированной атомарной транзакции инвентарь/кошелёк/журнал и способа миграции. Риск rollback кошелька к старому поколению при более новом журнале требует согласованной политики; не удалять журнал при обычной загрузке.
